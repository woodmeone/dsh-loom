# ADR-0004：尾部注入默认用 user 角色

- 状态：已接受
- 日期：2026-10-18

## 背景

服从强度的直觉排序是 `system < user < assistant`——同一段文字，放在 assistant 位置比放在 system 位置更「像模型自己说过的话」。所以尾部注入看起来应该用 assistant。

但 dsh 的通道能力不支持这个选择：

| 通道 | 能产出的角色 | 代价 |
|---|---|---|
| `systemPrompt.section()` | 只有 system | `PromptSection` 类型里没有 `role` 字段 |
| `agent/pre-step` 返回 `messages` | **只有 user** | 类型是 `UserMessage[]`，消费端每条硬编码记成 `user/message` |
| `session.append('assistant/message', …)` | assistant | 要自己造 `step/start` + `step/end` 包裹 |
| `systemPrompt.context()` | user（一条运行时快照） | 文本没变就不重发 |

`agent/pre-step` 里塞一个 assistant 角色对象**不会在 append 时被拒**（`Session.append()` 不校验 `data.message.role`），但会写脏持久日志，**下次加载必抛**：

```
user/message message must have role "user"
```

校验点在 `dsh-session` 的种子/加载边界，不在 append 路径上——**错误会延迟到下次启动才炸**。

另一边的证据：真实酒馆预设里，两个尾部槽用的都是 user。

```
sy_059  🔒起笔锁（user · 最后）
sy_060  📌强调玩家输入（user）
```

同一份预设 60 个槽的角色分布是 `system 58 / user 2 / assistant 0`。

## 决策与取舍

**尾部注入默认用 user。`role` 存成块级字段，不全局固定。**

按用途分流：

- **重申规则 / 强调输入 → user**（与酒馆实践一致，走 `agent/pre-step` 的免费通道）
- **起笔锁 / 预填 → assistant**（这才是 assistant 的正确用法：让模型直接接着写）

放弃了：

- **全局固定 assistant。** 要额外造 step 包裹，多一层可能出错的代码，而且「重申规则」这类内容用 assistant 语义上是错的——模型会把它读成自己讲过的话。
- **全局固定 user。** 丢掉 assistant 前文注入那一整类的表达能力。
- **把角色从位置推导。** 真实预设里角色和位置是独立的（58 个 system 混在各类位置上），推导会把那 2 个 user 槽全推成 system。

## 后果

- 角色由**块**决定，不由位置决定。`role` 是块的一等字段。
- 用 assistant 的块必须走 `session.append` 那条重通道，**不能再走 `agent/pre-step`**。
- **内容为空的 assistant 消息会被 surface 丢弃**（与 user 消息的行为不同），写这类块时要留意。
- 上游 `lib/net-scope.js` 的 `appendDenial()` 是 assistant 通道的现成范本，可以直接借。
